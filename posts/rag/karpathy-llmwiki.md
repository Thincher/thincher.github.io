# LLM Wiki

一种利用大语言模型构建个人知识库的模式。

这是一份理念文档，设计初衷是让你将其复制粘贴到自己的 LLM Agent 中（如 OpenAI Codex、Claude Code、OpenCode / Pi 等）。它的目标是传达核心思想，而具体的实现细节则由你的 Agent 与你协作完成。

## 核心理念

大多数人对 LLM 与文档交互的体验是 RAG（检索增强生成）：上传一批文件，LLM 在查询时检索相关片段，然后生成答案。这种方式可行，但 LLM 每次回答问题都要从零开始重新发现知识，毫无积累。问一个需要综合五份文档的精微问题，LLM 每次都得重新找到并拼凑相关片段，什么都没有沉淀。NotebookLM、ChatGPT 文件上传以及大多数 RAG 系统都是这样运作的。

这里的理念截然不同。LLM 不再仅仅在查询时从原始文档中检索，而是**渐进式地构建和维护一个持久的 Wiki**——一个结构化、相互链接的 Markdown 文件集合，它介于你和原始资料之间。当你添加新的资料时，LLM 不会仅仅为后续检索建立索引，而是阅读它、提取关键信息、将其整合到已有的 Wiki 中——更新实体页面、修订主题摘要、标注新旧数据的矛盾之处、强化或质疑不断演进的综合论述。知识只编译一次，然后*持续保持更新*，而非每次查询时重新推导。

这就是关键区别：**Wiki 是一个持久的、复利式增长的知识产物。** 交叉引用已经就位，矛盾之处已经标注，综合分析已经反映了你读过的所有内容。每添加一份资料、每提出一个问题，Wiki 都会变得更加丰富。

你无需（或极少需要）亲自撰写 Wiki——LLM 负责所有的撰写和维护。你的职责是寻找资料、探索方向、提出好问题。LLM 承担所有繁重工作——摘要提炼、交叉引用、归档整理、日常维护——正是这些工作让知识库随时间推移真正发挥作用。实际操作中，我一边开着 LLM Agent，一边开着 Obsidian。LLM 根据我们的对话进行编辑，我实时浏览结果——跟踪链接、查看图谱视图、阅读更新后的页面。Obsidian 是 IDE，LLM 是程序员，Wiki 是代码库。

这一模式适用于诸多场景。举几个例子：

- **个人成长**：追踪自己的目标、健康、心理状态、自我提升——归档日记条目、文章、播客笔记，逐步构建关于自己的结构化全貌。
- **学术研究**：在数周或数月内深耕某一主题——阅读论文、文章、报告，渐进式地构建一个带有演进论点的综合性 Wiki。
- **读书笔记**：逐章归档，为人物、主题、情节线索建立页面并梳理关联。读完全书后，你便拥有了一本丰富的伴读 Wiki。想想那些粉丝维基，比如 [Tolkien Gateway](https://tolkiengateway.net/wiki/Main_Page)——数千个相互链接的页面，涵盖人物、地点、事件、语言，由志愿者社区历时多年建成。你可以在阅读过程中由 LLM 完成所有交叉引用和维护，个人构建出类似的知识库。
- **商业/团队**：由 LLM 维护的内部 Wiki，以 Slack 线程、会议纪要、项目文档、客户通话为输入源。可引入人工审核更新内容。Wiki 能保持时效性，因为 LLM 承担了团队中无人愿意做的维护工作。
- **竞品分析、尽职调查、旅行规划、课程笔记、爱好深研**——任何需要随时间积累知识并希望其井然有序而非散乱无章的场景。

## 架构

共有三层：

**原始资料层**——你精心策展的源文档集合。文章、论文、图片、数据文件。这些是不可变的——LLM 从中读取但绝不修改。这是你的唯一可信源。

**Wiki 层**——由 LLM 生成的 Markdown 文件目录。摘要、实体页面、概念页面、对比分析、概览、综合论述。LLM 完全拥有这一层。它创建页面、在新资料到来时更新页面、维护交叉引用、保持一切的一致性。你来阅读，LLM 来撰写。

**Schema 层**——一份文档（如 Claude Code 的 CLAUDE.md 或 Codex 的 AGENTS.md），告诉 LLM Wiki 的结构如何组织、遵循什么约定、在摄入资料、回答问题或维护 Wiki 时应遵循什么工作流。这是关键的配置文件——正是它让 LLM 成为一个严谨的 Wiki 维护者，而非泛泛的聊天机器人。你与 LLM 随着时间推移共同演化这份文档，逐步摸索出适合你领域的方法论。

## 操作

**摄入（Ingest）。** 你将新资料放入原始资料集合并告知 LLM 处理。一个典型流程：LLM 阅读资料、与你讨论关键要点、在 Wiki 中撰写摘要页面、更新索引、更新 Wiki 中相关的实体和概念页面、在日志中追加一条记录。一份资料可能涉及 10-15 个 Wiki 页面。我个人倾向于逐一摄入资料并全程参与——阅读摘要、检查更新、引导 LLM 侧重哪些内容。但你也可以批量摄入大量资料而较少监督。如何开发适合自己风格的工作流并将其记录在 Schema 中以供后续会话使用，完全由你决定。

**查询（Query）。** 你针对 Wiki 提出问题。LLM 搜索相关页面、阅读它们，然后综合出带引用的答案。答案的形式因问题而异——Markdown 页面、对比表格、幻灯片（Marp）、图表（matplotlib）、画布。一个重要洞见：**好的答案可以作为新页面归档回 Wiki。** 你请求的对比分析、一项分析、你发现的关联——这些都很有价值，不应消失在聊天记录中。这样，你的探索就能像摄入的资料一样在知识库中复利积累。

**巡检（Lint）。** 定期让 LLM 对 Wiki 进行健康检查。查找：页面间的矛盾、已被新资料取代的过时论断、没有入站链接的孤立页面、被提及但缺少独立页面的重要概念、缺失的交叉引用、可通过网络搜索填补的数据空白。LLM 擅长建议值得探究的新问题和新资料来源。这确保 Wiki 在增长过程中保持健康。

## 索引与日志

两个特殊文件帮助 LLM（和你）在 Wiki 增长过程中导航。它们各有分工：

**index.md** 面向内容。它是 Wiki 中所有内容的目录——每个页面列出链接、一行摘要，以及可选的元数据如日期或资料数量。按类别组织（实体、概念、资料来源等）。LLM 在每次摄入时更新它。回答查询时，LLM 先读取索引找到相关页面，再深入阅读。这在中等规模（约 100 份资料、数百个页面）下效果出奇地好，无需基于嵌入的 RAG 基础设施。

**log.md** 按时间排列。它是一条只追加的记录，记载了何时发生了什么——摄入、查询、巡检。一个实用技巧：如果每条记录以一致的前缀开头（如 `## [2026-04-02] ingest | Article Title`），日志就可以用简单的 Unix 工具解析——`grep "^## \[" log.md | tail -5` 即可获取最近 5 条记录。日志为你提供了 Wiki 演化的时间线，也帮助 LLM 了解近期做了什么。

## 可选：CLI 工具

在某个阶段，你可能想构建一些小工具来帮助 LLM 更高效地操作 Wiki。最显而易见的是 Wiki 页面的搜索引擎——小规模时索引文件就够了，但随着 Wiki 增长，你需要正式的搜索功能。[qmd](https://github.com/tobi/qmd) 是一个不错的选择：它是 Markdown 文件的本地搜索引擎，支持混合 BM25/向量搜索和 LLM 重排序，全部在设备本地运行。它既有 CLI（LLM 可以通过 shell 调用），也有 MCP 服务器（LLM 可以将其作为原生工具使用）。你也可以自己构建更简单的方案——LLM 可以帮你随性编码一个简单的搜索脚本，按需开发即可。

## 技巧与窍门

- **Obsidian Web Clipper** 是一个浏览器扩展，可将网页文章转为 Markdown。非常适合快速将资料收入原始资料集合。
- **本地下载图片。** 在 Obsidian 设置 → 文件与链接中，将"附件文件夹路径"设为固定目录（如 `raw/assets/`）。然后在设置 → 快捷键中搜索"Download"，找到"下载当前文件的附件"并绑定快捷键（如 Ctrl+Shift+D）。剪藏文章后按快捷键，所有图片即下载到本地磁盘。这是可选的但很有用——它让 LLM 能直接查看和引用图片，而不依赖可能失效的 URL。注意，LLM 无法一次性原生读取含内联图片的 Markdown——变通方法是让 LLM 先读文本，再单独查看部分或全部引用的图片以获取额外上下文。略显笨拙但足够好用。
- **Obsidian 的图谱视图**是查看 Wiki 形态的最佳方式——什么与什么相连、哪些页面是枢纽、哪些是孤岛。
- **Marp** 是基于 Markdown 的幻灯片格式。Obsidian 有对应插件。适合直接从 Wiki 内容生成演示文稿。
- **Dataview** 是 Obsidian 插件，可对页面 frontmatter 执行查询。如果你的 LLM 在 Wiki 页面中添加了 YAML frontmatter（标签、日期、资料数量），Dataview 可以生成动态表格和列表。
- Wiki 本质上就是一个 Markdown 文件的 Git 仓库。版本历史、分支、协作，开箱即用。

## 为什么这行得通

维护知识库的枯燥部分不是阅读或思考——而是日常维护。更新交叉引用、保持摘要时效性、标注新旧数据的矛盾、维护数十个页面间的一致性。人们放弃 Wiki 的原因在于维护负担的增长速度远超其价值。LLM 不会厌倦，不会忘记更新交叉引用，一次操作就能触及 15 个文件。Wiki 得以保持维护，因为维护成本近乎为零。

人的职责是策展资料、引导分析、提出好问题、思考一切意味着什么。LLM 的职责是其余的一切。

这一理念在精神上与 Vannevar Bush 的 Memex（1945）一脉相承——一个个人的、精心策展的知识存储，文档之间有联想式的关联路径。Bush 的愿景更接近于此，而非当今互联网的形态：私有的、主动策展的，文档之间的关联与文档本身同样有价值。他未能解决的是谁来承担维护工作。LLM 解决了这个问题。

## 备注

本文档有意保持抽象。它描述的是理念，而非具体实现。确切的目录结构、Schema 约定、页面格式、工具链——这一切都取决于你的领域、偏好和所选的 LLM。上述所有内容都是可选的、模块化的——取其有用，弃其无用。例如：你的资料可能纯文本，完全不需要图片处理；你的 Wiki 可能足够小，索引文件就够用了，无需搜索引擎；你可能不在乎幻灯片，只要 Markdown 页面；你可能想要完全不同的输出格式集。正确的使用方式是将本文档分享给你的 LLM Agent，共同打造一个适合你需求的版本。本文档的唯一职责是传达这一模式，你的 LLM 能搞定其余的一切。

## 我的理解

Karpathy 提出的 LLM Wiki 模式，本质上是对「人机协作知识管理」的一次范式革新。以下是我的几点理解：

**1. 从「即时检索」到「持续编译」**

RAG 的问题不在于检索不准，而在于它永远在做「一次性推理」——每次提问都从原始文档重新出发，像是一个从不记笔记的学生每次考试都翻课本。LLM Wiki 的核心洞见是：知识的价值在于**沉淀与关联**，而非即时检索。将知识编译一次、持续维护，远比每次重新推导高效。

**2. 复利效应是灵魂**

「复利式增长的知识产物」这个定位极为精准。传统笔记系统之所以荒废，是因为维护成本随规模非线性增长，而价值增长却是线性的——入不敷出。LLM 将维护成本压至近零，使得知识库的价值曲线终于能跑赢成本曲线。每一次摄入、每一次查询、每一次巡检，都在为知识库增值，而非仅仅消耗。

**3. 三层架构的精妙分工**

原始资料层（不可变）→ Wiki 层（LLM 生成维护）→ Schema 层（人机共治），这个分层设计暗合了软件工程中「数据-逻辑-配置」的经典架构。原始资料是 Source of Truth，Wiki 是 Derived View，Schema 是 Business Logic。这种分离确保了可追溯性、一致性和可演化性。

**4. 人的角色升维**

人从「知识搬运工」升维为「知识策展人」。你不再需要做摘要、建索引、维护交叉引用——这些机械劳动交给 LLM。你专注于只有人才能做的事：判断什么值得读、提出有深度的问题、发现跨领域的关联、做出价值判断。这是对人类认知资源的重新分配。

**5. 与 Memex 的跨时空呼应**

Bush 在 1945 年就预见到了个人知识网络的价值，但他无法解决「谁来维护」的问题。近 80 年后，LLM 终于给出了答案。这不仅是技术进步，更是对一种古老理想的实现——让知识之间的关联与知识本身同等重要，而维护这些关联不再是人类的负担。

**6. 实践中的关键挑战**

尽管理念优雅，实践中仍有挑战：Schema 的设计需要领域知识，Wiki 的质量取决于 LLM 的理解深度，大规模下的索引和搜索仍需工程投入。但正如 Karpathy 所说，这些都是模块化、可选的——核心理念足够简单，你可以从最简版本开始，渐进演化。

总而言之，LLM Wiki 不是又一个笔记工具或 RAG 方案，而是一种**将 LLM 作为知识协作者**的思维转变。它让知识管理从「存储-检索」模式进化为「编译-维护-增长」模式，这可能是个人知识管理领域近年来最具启发性的构想之一。
